- #fetch:https://docs.nautobot.com/projects/golden-config/en/latest/user/app_feature_compliance/

  - CLI compliance uses line-start matching (implicit greedy)
  - JSON compliance compares top-level keys of structured data
  - Devices can be in/out of scope via Dynamic Groups
  - Compliance jobs compare intended vs actual configs per feature per device

- #fetch:https://docs.nautobot.com/projects/golden-config/en/latest/user/app_feature_intended/

  - Templates use `config_context` (vendor-neutral JSON) from Nautobot's device model

  - Backup and intended configs stored in Git repos as JSON files

## Key Discoveries

### Nautobot Integration Architecture

Nautobot Golden Config operates on a fundamentally different paradigm from Aegis's script-based enforcement:

1. **Aegis Current Model (Script-Based)**: LLM generates Python scripts that are `exec()`'d to check device state via connectors. The code actively queries devices and evaluates compliance programmatically.

2. **Nautobot Golden Config Model (Data-Driven)**: Uses "intended configuration" (CLI or JSON) as the golden standard. Compliance is determined by comparing the intended config to the device's actual running config — no executable code needed.

### Integration Points with Nautobot

For Aegis to push golden configurations to Nautobot, the key integration points are:

1. **Nautobot REST API** — Device management, config contexts, and the Golden Config plugin API
2. **Git Repositories** — Nautobot reads intended configs from Git repos; Aegis can push generated configs to these repos
3. **Config Contexts** — Nautobot's `config_context` provides structured (JSON) device data used in Jinja2 template rendering
4. **Compliance Rules** — Define which configuration features to monitor per platform
5. **Golden Config Jobs API** — Trigger backup, intended generation, and compliance jobs

### Two Viable Integration Approaches

**Approach A: Direct Intended Config Push (via Git)**
- Aegis generates the intended configuration (CLI text or JSON) using LLM
- Pushes it to Nautobot's configured Git repository for intended configs
- Nautobot's compliance engine periodically compares against device backup
- Best for CLI-based devices (network switches)

**Approach B: Config Context + Jinja2 Template Push (via Nautobot API)**
- Aegis generates structured data (JSON config_context) representing the golden state
- Pushes config_context to Nautobot's device records via REST API
- Nautobot renders intended config from the data + Jinja2 templates already in its repo
- More "Nautobot-native" but requires templates to exist in Nautobot

### LLM Generation Difference: Script vs Data-Driven Config

| Aspect | Script-Based (Current) | Data-Driven (Nautobot) |
|--------|----------------------|----------------------|
| Output | Python code using `connector.run_command()` | CLI config text or JSON structure |
| Execution | `exec()` in Aegis worker | Nautobot compares text/JSON diffs |
| Scope | Evaluation + Remediation + Rollback | Evaluation only (intended vs actual) |
| Drift Detection | Active (Aegis schedules jobs) | Passive (Nautobot monitors continuously) |
| Remediation | Aegis `remediation_code` | Nautobot's Config Plans/Remediation engine |
| Rollback | Aegis `rollback_code` | Not applicable (Nautobot tracks previous configs in Git) |

### Data-Driven Golden Configuration Format

For network switches (primary use case), the golden config would be CLI-format intended configuration:

```text
! Security Hardening - Golden Configuration
! Generated by Aegis from CIS Network Switch Benchmark
!
ip ssh version 2
line vty 0 15
 transport input ssh
 no transport input telnet
!
no ip http server
no ip http secure-server
no snmp-server community public
no snmp-server community private
!
aaa new-model
aaa authentication login default group tacacs+ local
!
banner login ^
WARNING: Unauthorized access to this device is prohibited.
^
```

For JSON-based compliance:

```json
{
  "ssh": {
    "version": 2,
    "transport_input": "ssh",
    "telnet_enabled": false
  },
  "services": {
    "http_server": false,
    "https_server": false,
    "snmp_v1_v2c_enabled": false,
    "snmp_v3_enabled": true
  },
  "aaa": {
    "new_model": true,
    "authentication": "group tacacs+ local"
  }
}
```

## Recommended Approach

**Approach A: Direct Intended Config Push via Nautobot REST API + Git Repository**

This approach is recommended because:
- It aligns with Nautobot's native architecture (intended config files in Git repos)
- Supports both CLI and JSON compliance types
- Minimizes coupling — Aegis generates and pushes; Nautobot monitors independently
- Leverages existing Nautobot compliance engine for continuous drift detection
- Does not require modifying Nautobot's Jinja2 templates

**Integration Flow:**
1. User selects "Nautobot Golden Config" evaluation method for a Policy/Blueprint
2. LLM generates **data-driven intended configuration** (CLI text or structured JSON) instead of Python evaluation scripts
3. Generated config is stored in `PolicyRule.golden_config_data` / `BlueprintRule.golden_config_data`
4. On "Push to Nautobot" action, Aegis:
   a. Commits the intended config file to the Nautobot-configured Git repo (using GitPython or bare HTTP)
   b. Optionally updates Nautobot device `config_context` via REST API
   c. Triggers a Nautobot compliance job via the Jobs API
5. Nautobot continuously monitors device compliance against the golden config
6. Remediation and rollback remain script-based in Aegis (not pushed to Nautobot)

## Implementation Guidance

- **Objectives**:
  - Add an alternative evaluation method (`nautobot_golden_config`) alongside existing script-based approach
  - Generate data-driven configuration (CLI/JSON) using LLM for network device policies
  - Push generated golden configs to Nautobot for continuous drift monitoring
  - Keep script-based evaluation/remediation/rollback as the default and for non-network devices

- **Key Tasks**:
  1. Add `evaluation_method` enum field to `PolicyRule` and `BlueprintRule` models (`script` default, `nautobot_golden_config` option)
  2. Add `golden_config_data` Text/JSON column to store the generated intended configuration
  3. Add `golden_config_format` enum (`cli` | `json`) to indicate the config type
  4. Create new LLM prompt template `GOLDEN_CONFIG_CLI_TEMPLATE` and `GOLDEN_CONFIG_JSON_TEMPLATE`
  5. Extend `CodeGenerator` with `generate_golden_config()` method
  6. Create `NautobotConnector` service class (`backend/aegis/services/connectors/nautobot_connector.py`)
  7. Add Nautobot settings to `config.py`: `NAUTOBOT_URL`, `NAUTOBOT_API_TOKEN`, `NAUTOBOT_GOLDEN_CONFIG_REPO`
  8. Create Celery task `push_golden_config` in a new or existing task module
  9. Add API endpoints: `POST /policies/{id}/generate-golden-config`, `POST /instances/{id}/push-nautobot`
  10. Add DB migration for new columns
  11. Update frontend PolicyRule display and enforcement console to support the new method
  12. Add UI toggle for selecting evaluation method (script vs nautobot) at Policy/Blueprint level

- **Dependencies**:
  - `httpx` or `requests` for Nautobot API calls (requests already in requirements.txt)
  - `gitpython` for Git repo operations (optional — can also use HTTP API to push files)
  - Nautobot instance with Golden Config plugin installed and configured
  - Git repository accessible by both Aegis and Nautobot for intended config files

- **Success Criteria**:
  - User can select "Nautobot Golden Config" as evaluation method per PolicyRule/BlueprintRule
  - LLM generates valid CLI or JSON intended configuration from policy rules
  - Generated config is pushable to Nautobot via API
  - Nautobot successfully runs compliance checks against the pushed golden config
  - Script-based evaluation/remediation/rollback remain fully functional as default
  - Frontend clearly indicates which method is active and provides appropriate controls
